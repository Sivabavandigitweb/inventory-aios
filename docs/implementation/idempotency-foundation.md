## Implemented components

`app.models.IdempotencyRequest` is one shared table mapping for future receiving, allocation, return, approval, disposal and employee-exit commands. It references the existing `users` table by `principal_id` with ON DELETE RESTRICT. UUID `id` has Python and PostgreSQL `gen_random_uuid()` defaults. `operation_scope`, `idempotency_key`, lowercase SHA-256 `request_fingerprint` and `status` are required. `status` is constrained to `processing` or `succeeded`. A successful record has a 2xx `response_status`, a timezone-aware `completed_at`, and an optional paired `resource_type`/`resource_id` reference; processing records have no result fields. Standard created/updated timestamps follow the existing model mixin. There is no response body, raw request payload, authentication credential, cached failure, expiry or cleanup field. The pair is a minimal stable reference, not a guarantee that every future operation can be fully replayed from that reference; each command must define its safe replay contract.

A named unique constraint covers `(principal_id, operation_scope, idempotency_key)`. Named CHECKs validate nonblank scope/key, SHA-256 syntax, status, result completeness and resource pairing. A `(principal_id,status)` index supports scoped operational review; the unique index covers key lookup. The model does not assert that a `processing` row cannot be committed: that property needs a future transactional runner and integration tests. Resource targets are deliberately typed as a string/UUID pair because workflow tables are not yet implemented; they are not a database foreign key. Each future command must verify resource existence and visibility before returning it. The model uses explicit `public` schema while the existing User mapper is schema-unqualified; a future migration must explicitly qualify `public.users` without changing the original migrations.

`fingerprint_request` hashes a versioned operation scope and a canonical, validated command representation. Object key order is sorted, array order is retained, NFC Unicode is applied to strings/keys, aware datetimes are converted to UTC, and finite Decimal values are represented exactly without decimal-context rounding. Integers, booleans, strings, null, UUID and date remain distinct tagged types. Bytes, floats, naive datetimes, non-string keys, cycles, excess depth/size and keys suggesting credentials or tokens are rejected with a generic error. Sensitive values are never included in error text or logs by this utility. Callers must pass only validated non-secret command fields. SHA-256 provides equality, **not confidentiality**: a low-entropy serial, cost or other value may be guessed from its digest. Store and expose fingerprints only under narrowly scoped access. Version the operation scope whenever canonicalization rules change.

`decide_request` is pure: it receives an authenticated `Principal`, key, fingerprint, optional scoped snapshot and two injected authorization checks. It validates the request shape, checks current operation permission, rejects a snapshot from another principal/scope/key without revealing its contents, checks result visibility before fingerprint comparison, and returns either execute or a minimal successful replay. It raises safe conflicts for changed content or in-progress records and fails closed on malformed completed records. It never opens a session, claims a key, flushes, commits, rolls back, calls audit, or supplies an actor from request data. The injected checks must reload current authorization at the API/service boundary; the offline component cannot itself prove provider or database authorization. Future AI suggestions must enter the same authenticated command path.

## Deferred runtime behavior and security gates

The future command runner must claim the `(principal,scope,key)` unique key in the caller's transaction, handle unique violations through PostgreSQL savepoints or `ON CONFLICT`, wait within a bounded engineering policy, and recheck authorization on every replay. It must write business effects, audit events and a succeeded result in one transaction. A failed business/audit operation rolls back the claim and effects. A server crash after commit must replay the saved minimal result without a duplicate effect. A committed `processing` row is an incident requiring investigation; no automatic stale lease recovery is implemented. The result callback must recheck resource visibility, including changed roles and scope, before returning any reference. A different key still goes through business duplicate and approval constraints.

Future runtime privileges will be derived from the actual ORM statements: narrow INSERT on claim fields, UPDATE on result/status fields, and scoped SELECT needed for unique-key resolution and replay. PostgreSQL grants alone cannot enforce per-principal row visibility; authorization must query by principal and recheck resource scope. No privilege is granted by this task. R-11 remains partial and audit writes remain pending separate approval. Idempotency does not replace audit or an approved business workflow.

ABD-13 asks management how long late retries must be protected and how long minimal confirmation data may remain. No fixed TTL, expiry default, automatic deletion, response-body retention or failure cache is approved. Any later cleanup must preserve uniqueness during the agreed retry window, respect referenced history and have a separately reviewed recovery plan. Other asset decisions and employee registration remain pending.

Review timestamp trigger reuse and explicit `public.users` FK qualification. Inspect ownership, default/PUBLIC function EXECUTE and table ACLs; runtime grants require separate approval. Do not modify existing revisions. Before migration execution, verify the target revision, checksum-backed backup, baseline ownership/ACL/rows, recovery procedure and disposable-database rehearsal. Offline metadata compilation does not establish live PostgreSQL behavior.

Required future PostgreSQL tests: concurrent same-key claims on separate connections; winner commit versus rollback; changed-fingerprint conflict; bounded wait/timeout and deadlock retry; crash-after-commit replay; no duplicate business/audit effects; authorization revocation and cross-principal isolation; malformed or durable processing records; constraint SQLSTATEs; least-privilege runtime writes/reads; transactional rollback of audit and claim; optional resource references; and backup/recovery. Do not run the existing PostgreSQL integration suite during Task 8D.

Offline verification checks model metadata, FK/relationship, PostgreSQL DDL compilation, fingerprint stability/distinctions and failure safety, authorization callbacks, replay/conflict decisions, and absence of transaction control. These checks cannot prove concurrency or database constraint enforcement.
