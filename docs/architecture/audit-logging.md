# Audit logging foundation

The requirements PDF defines R-11 as recording the user, date and time, previous value, and updated value for changes, with history available for audit and management review. The requirements matrix preserves that source wording. The foundation below is partial and does not claim full R-11 compliance.

Revision 7d4a9c2e1b60 has been applied to the disposable inventory_aios_restore_check rehearsal database only. It has not been applied to inventory_aios_dev. The table, model, and writer provide an append-only event envelope with actor, timestamp, entity, source, and constrained JSONB metadata.

Metadata accepts only a UUID request ID, up to 20 unique changed-field names, and a success or failure outcome. It rejects unknown keys, nested values, invalid types, and sensitive field names. PostgreSQL validates the same contract. The audit writer flushes through the caller's SQLAlchemy session and does not commit or suppress failures. Employee registration still fails closed through its unavailable audit-writer dependency.

The actual SQLAlchemy flush supplies the UUID from the model's Python default and uses RETURNING for the server-generated occurred_at value. The finalized proposed runtime privilege set is column-level INSERT(id, actor_user_id, action, entity_type, entity_id, change_source, metadata) on public.audit_events, column-level SELECT(occurred_at), and EXECUTE on public.inventory_aios_audit_metadata_is_valid(jsonb). INSERT(occurred_at), table-level INSERT and table-level SELECT are denied. It does not require table-level SELECT, SELECT on the UUID column, sequence privileges, or SELECT on the referenced users table. These grants have not been applied permanently. The administrator-assisted rollback rehearsal now verifies the actual writer with current_user=inventory_aios_app and session_user=postgres. Direct runtime connection tests separately verify that the application login cannot assume owner or migrator roles. No role memberships were added.

This permission set would let a compromised runtime credential fabricate additional events using allowed values and actor IDs it can obtain; the database does not bind actor_user_id to the authenticated API principal. The service must derive actor identity from authenticated and authorized backend context and validate event/entity semantics. Clients and future Grok AI integrations must never independently supply trusted actor identities. Authentication-provider selection and mapping provider subjects to local users remain outstanding. Management must approve whether that trust boundary and event policy are acceptable before enabling runtime audit writes. The proposed SELECT(occurred_at) privilege permits querying timestamps across audit records; it is not limited to RETURNING the caller's new row. Other audit columns remain unreadable. Whether timestamp visibility is acceptable requires an explicit policy decision.

R-11's previous-value and updated-value fields are not implemented. The current changed_fields metadata stores field names only. An approved field-level redaction and confidentiality policy is required before values can be logged. Authorized audit-history queries, filtering/reporting, and retention, archival, legal-hold, backup, and deletion policy also remain outstanding.

The migration installs UPDATE, DELETE, and TRUNCATE rejection triggers. Corrections must be represented by new compensating events. These triggers protect against ordinary DML, not an owner or superuser disabling them.

## Decisions still required

- Whether and how to record before/after values, with a field-level redaction policy.
- Whether runtime credentials may submit events and how actor attribution is protected against fabricated events.
- Which event types and metadata are approved, including whether failed authentication/security events belong in this stream.
- Which roles may query audit history, their organizational scope, and whether exports are allowed.
- Retention, archival, legal hold, backup, deletion authority, and emergency correction procedures.
- Operational ownership and review of the proposed narrow runtime grants before any application path is enabled.

No runtime audit grants have been applied. Employee registration remains disabled.

## Stage 7 administrator-assisted runtime rehearsal

The explicit opt-in test `tests/test_audit_admin_rehearsal.py` connects only as postgres to localhost:5432/inventory_aios_restore_check using libpq authentication. Run it only with authorized administrator access and process-local `INVENTORY_ADMIN_AUDIT_REHEARSAL=1`. It uses NullPool, one connection, one outer transaction, and SQLAlchemy sessions bound to that connection with create_savepoint transaction joining. An outer-commit event guard rejects commits. A Session.commit probe releases only its savepoint. Cleanup rolls back the outer transaction even after failure, then compares role memberships, role attributes, database/schema/object ACLs and ownership, constraints, functions, triggers, column ACLs, default ACLs and all public-table row hashes against the baseline. No row contents or credentials are printed.

The real writer succeeds with the three candidate grants. Expected failures use savepoints and verify SQLSTATE 23503 for unknown actors, 23514 for invalid metadata, and 42501 for unauthorized reads, mutations, truncation, trigger changes and table structure changes. All temporary grants, actors and events disappear on rollback.

The finalized 06 grant script uses INSERT privileges on exactly id, actor_user_id, action, entity_type, entity_id, change_source and metadata, together with SELECT(occurred_at) and validator EXECUTE. The rehearsal loads that actual script, removes only its psql transaction wrapper, and executes its body inside the protected outer transaction. Local session authorization is temporarily set to the migrator so the unchanged identity guards and explicit owner role assumption are exercised, then reset to postgres before SET LOCAL ROLE inventory_aios_app. The actual writer succeeds and an explicit occurred_at INSERT is denied with 42501. PostgreSQL must generate audit timestamps. The script verifies effective rights on every audit column, denies table-wide privileges, and preserves existing runtime reads. Permanent application remains pending separate management approval. Supplying the ID remains necessary for the current ORM Python UUID default. Removing RETURNING or its SELECT requirement would require an explicitly reviewed writer/model change; it was not changed by this rehearsal.

The proposed application-controlled architecture requires business changes and audit events to use the same database transaction and derives actors from authenticated request context, but a stolen runtime database credential can bypass that application policy and fabricate actor, action, entity, source and event IDs. Foreign keys prove that an actor exists, not that the actor performed the action. Database-controlled triggers can capture actual row changes and before/after values, but a shared runtime login or client-set actor context still does not independently prove the human identity. Stronger attribution requires a trusted identity boundary, such as separately verified signed actor claims or an independent audit service with credentials unavailable to the runtime; this adds operational complexity and does not by itself supply missing before/after history.

For the current foundation, recommend the existing caller-transaction writer, server-derived actor context at the authorized service boundary, column-level INSERT, server timestamps, append-only constraints and restricted audit readers. This is a recommendation, not approval of the shared-runtime trust model. Management must approve actor-attribution assurance, permitted event/source policy, timestamp visibility, redaction and before/after value requirements, audit reader scope and retention. No SECURITY DEFINER function, new role, membership, migration or writer redesign was introduced. Employee registration and persistent runtime audit writes remain disabled.

Implementation tasks, policy decisions, and approval boundaries are tracked in [Audit permission readiness](../implementation/audit-permission-readiness.md). R-11 remains partially implemented. Append-only protection does not provide independently verified actor attribution.

## Authentication accountability direction (proposed)

For the selected initial development direction, user-originated events should identify the authenticated individual Inventory AIOS account by its stable local `users.id`. Never accept an actor ID from a client, Management AIOS request, or Grok output as proof of the actor. A future summary-only service identity must not be treated as a human administrator or receive audit-write capability. Passwords, password hashes, session tokens, reset capabilities, and service credentials must never be placed in audit metadata. R-11 before/after values, sensitive-field redaction, audit readers/exports, retention, and the trust boundary for application-controlled audit insertion remain Pending Approval. The rehearsal evidence is not operational audit activation; runtime grants and writes remain disabled.

Draft revision `9c81e247a610` adds nullable `previous_values` and `updated_values` JSONB fields. The application builder currently accepts only selected lifecycle/status/unit/quantity fields and rejects free text, employee names, serials, procurement costs, credentials, and tokens. The migration constrains the values to JSON objects; database-side key/value allowlisting, runtime privilege scope, and populated-data downgrade behavior require PostgreSQL rehearsal. This does not complete R-11 or activate audit writing.
