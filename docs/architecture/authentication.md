## Task 10C provider-independent hardening

Offline hardening validates opaque bearer input before verification, requires a UUID identity result, conceals unmapped/inactive account distinctions, confirms the returned local row matches the mapped UUID, and rejects malformed permission-policy results and wildcard capabilities. Current role assignments are fetched again per request with both `valid_from` and `valid_to` bounds, so role removal or expiry is reflected on the next authorization check. Authentication and role-query SQLAlchemy failures are rolled back and mapped to safe service-unavailable responses; there are no retries or extra pools.

The response contract is: missing credentials `401 AUTHENTICATION_REQUIRED`; malformed, invalid, unmapped, or inactive credentials `401 INVALID_CREDENTIALS`; unconfigured or recognized verifier outage `503 AUTHENTICATION_UNAVAILABLE`; identity/role lookup availability failures `503 AUTHENTICATION_UNAVAILABLE` or `503 AUTHORIZATION_UNAVAILABLE`; permission denial `403 FORBIDDEN`; explicit policy outage or invalid policy output `503 AUTHORIZATION_UNAVAILABLE`; unexpected verifier/policy defects `500 INTERNAL_SERVER_ERROR` with a generic body. Request IDs remain available. No password, account provisioning, session, permission grant, audit write, or database schema change is implemented. Unexpected adapter failures are logged only as generic failure events, without exception text or credentials.

## Password hashing service boundary (Tasks 10F.1 and 10F.1A)

`backend/app/core/password_hashing.py` defines an injectable `PasswordHashBackend` protocol and a fail-closed `PasswordHashingService` wrapper. `backend/app/core/argon2_passwords.py` supplies an explicit Argon2id implementation using the maintained high-level `argon2-cffi` `PasswordHasher` API. The adapter generates salts through the library, returns its PHC representation, verifies passwords, and detects parameter drift with `check_needs_rehash`. Passwords pass unchanged: no Unicode normalization or truncation occurs. The service separates password-creation policy from hashing, treats mismatch or unsafe stored encoding as a non-match, and maps provider failures to a generic error without logging password or hash material.

The authorized dependency range `argon2-cffi>=25.1,<26` is declared in `backend/pyproject.toml` and installed in the existing backend virtual environment. Tested versions are argon2-cffi 25.1.0, argon2-cffi-bindings 26.2.0, cffi 2.1.1, and pycparser 3.12. The install used the existing project venv and did not upgrade unrelated packages. The authorized command was `python -m pip install "argon2-cffi>=25.1,<26"` from `backend/`. See the [argon2-cffi API](https://argon2-cffi.readthedocs.io/en/stable/api.html) and [password hashing guide](https://argon2-cffi.readthedocs.io/en/stable/howto.html).

The adapter has no implicit cost or input-limit defaults: callers must supply generation parameters and separate verification/resource ceilings. Tests use explicitly bounded costs (1,024 KiB, time 2, parallelism 1, 16-byte salt, 32-byte hash) and an explicitly configured test-only 4 KiB UTF-8 password limit. This does not set an operational input cap. Before invoking expensive verification, the adapter uses the library's `extract_parameters` helper and rejects malformed encodings, non-Argon2id algorithms, unsupported versions, costs outside configured ceilings, overlong salts/tags, and oversized PHC strings. Older hashes within the accepted safe envelope can be verified and marked for rehash. The adapter is not instantiated by production authentication and is not connected to account lookup, persistence, routes, sessions, or audit writing.

Task 10F.1A tests include actual Argon2id hash/verify/salt/rehash operations with fictional passwords, plus mocked failure paths proving unsafe parameters are rejected before expensive verification. Fake-provider tests remain separate. These tests do not establish production cost suitability, authentication readiness, database enforcement, concurrency behavior, or deployment security. See [RFC 9106 §4](https://www.rfc-editor.org/rfc/rfc9106.html).

Argon2id cost parameters remain deployment decisions, not approved constants. RFC 9106’s first recommended profile is `m=2^21 KiB` (2 GiB), `t=1`, `p=4`, 16-byte salt, and 32-byte tag; its memory-constrained profile is `m=2^16 KiB` (64 MiB), `t=3`, `p=4`, the same salt/tag lengths. The current argon2-cffi low-memory defaults correspond to the latter profile but can vary by platform, so do not rely on implicit defaults. Benchmark explicitly constructed candidates on representative container/serverless limits and under concurrent login load, considering memory multiplied by parallel verification count. No expensive benchmark was run. Refer to [RFC 9106 §4](https://www.rfc-editor.org/rfc/rfc9106.html).

The service does not enforce the proposed 15-character minimum, composition rules, or an operational maximum length. The adapter requires an explicit UTF-8 byte limit as a resource-safety setting; its 4 KiB test setting is not an approved production policy. Empty/non-text new-password inputs are rejected as structurally unusable, while empty verification attempts fail as mismatches. Any operational bound must be approved, reject rather than truncate, and not make existing credentials unverifiable. Stored hash parameters are checked before verification to bound resource use. A successful future authentication may trigger transactional parameter rehashing while preserving credential-version and session-revocation semantics. Parameter-only rehashing is distinct from a password change/reset and does not by itself increment the credential version or revoke sessions.

Unknown usernames and wrong passwords must eventually share externally indistinguishable behavior. A generic response alone does not prevent timing-based account enumeration; orchestration should use a dummy hash path for unknown users and consistent throttling, and benchmark timing without logging submitted usernames, passwords, or hashes. Distributed throttling is needed before multi-instance/serverless exposure. Password policy, MFA, rate limiting, input cap, recovery, and operational activation remain Pending Approval under AUTH-02–AUTH-06. Task 10F.1A has completed the offline adapter under explicit dependency authorization; Task 10F.2 is limited to offline credential-verification orchestration and does not activate authentication.

## Offline credential verification orchestration (Task 10F.2)

`backend/app/core/credential_verification.py` defines injected user-identity and password-credential repository protocols, a username canonicalization contract, minimal immutable identity/credential projections, and an offline orchestration service. The service accepts only exactly one matching local identity with status `active`, a matching positive credential version, and a valid password. It returns only local user UUID, credential-version snapshot, and a rehash recommendation. It does not return hashes/passwords, roles, permissions, or session data; a successful result does not authenticate an API request, complete MFA, create a session, or grant access.

Unknown, inactive, missing-credential, and incorrect-password conditions use the same rejection class and fixed public message; a non-sensitive internal reason is retained for application handling. Ambiguous or inconsistent repository data and repository/provider failures fail closed with generic unavailable errors. For lookup misses and other denials that did not already perform password verification, an injected pre-generated dummy hash causes one bounded verification attempt whose result is always ignored. A wrong password against an existing supported hash already performed verification, so it does not incur a second dummy KDF. No production dummy hash, identity canonicalizer, repository implementation, route, retry, logging, or throttling default is provided.

Username normalization is intentionally injected. The current tests use a fictional case-folding canonicalizer only; that does not approve NFC/casefold rules or resolve their mismatch with PostgreSQL `lower(username)`. Analyze existing username collisions and database/application equivalence before provisioning or login activation. The service does not modify usernames, merge identities, create accounts, or assign roles.

Rehash need is checked against the current adapter before password verification so malformed, unsupported, or unsafe hashes can be rejected and receive dummy work. A successful result may carry `rehash_recommended`; this task never generates or persists a replacement hash, changes `credential_version`, or revokes sessions. Parameter-only rehash remains distinct from a user password change/reset. Before future session issuance, the service's user-active and credential-version observations must be revalidated atomically against current state so a deactivation or password reset cannot be bypassed by a stale result.

Dummy verification is a timing-hardening measure, not a constant-time guarantee. Hash parameter differences, runtime scheduling, repository lookup, and concurrent load can still distinguish paths. Perform deployment-representative timing analysis and approve distributed rate limiting and concurrency controls before activation. The service is not wired to `CredentialVerifier`, database persistence, role authorization, session lifecycle, MFA, account provisioning, or audit writing; the production verifier remains unconfigured and fail-closed.

## Session lifecycle service (Task 10F.3)

The backend/app/core/sessions.py module provides offline session issuance, validation, activity tracking, and revocation through injected session/account repositories and an injected clock. It matches the prepared public.auth_sessions contract: local session UUID, stable user UUID, credential-version snapshot, token_hash digest (represented internally as token_digest), created_at, last_seen_at, absolute expires_at, and nullable revoked_at. No database-backed repository is implemented.

Session tokens use secrets.token_urlsafe(32): 32 CSPRNG bytes represented as exactly 43 canonical unpadded URL-safe Base64 characters. The service validates that format, then stores/passes only SHA-256 of the ASCII token representation as a 32-byte digest. Raw tokens exist only on a dedicated immutable IssuedSession; its representation omits the token, generic JSON/pickle serialization is rejected, and the explicit token_for_cookie_delivery() accessor is reserved for a future secure cookie boundary. The token is returned only after persistence reports success. A repository must signal a digest uniqueness collision with the dedicated collision exception; only that condition receives at most three generation attempts. Other persistence failures return no token and are not retried.

SessionPolicy requires explicit absolute lifetime, idle timeout, activity update interval, and a separately supplied maximum-lifetime safety ceiling. Tests use explicit 8-hour absolute / 30-minute idle / 5-minute write-throttle values; these are not approved operational settings. Expiry checks use UTC-aware timestamps and exact now >= deadline semantics. Clock reversal, naive times, inconsistent row timestamps, malformed tokens, stale credential versions, missing credentials, inactive accounts, and revoked rows fail closed. Current roles and permissions are not stored in session results.

Issuance consumes the internal VerifiedCredential result, re-reads active status and credential version, then calls the repository's create_if_current. A future database implementation must make insertion conditional on active account state and the same current credential version in one transaction; the service's earlier read alone cannot prevent reset/deactivation races. The service is a lower-level credential-session component and does not decide whether MFA is required or complete; future login orchestration must enforce the approved factor policy before calling it.

Validation hashes the supplied canonical token, loads by digest, checks digest/identifier/timestamp consistency, revocation, absolute expiry, idle deadline, active user, and existing/current credential version. Activity updates occur only after validation and never modify absolute expiry or move last_seen_at backward. A bounded write interval can make recorded activity lag real use by up to that interval, shortening an idle session early; it must not extend access after the idle deadline. The repository update contract is conditional on expected user/version/activity and must atomically confirm the session remains unrevoked/unexpired and account/credential state is current. If another request advanced activity, the service reloads instead of overwriting it.

Individual revocation is idempotent and preserves the first revoked_at; records are not deleted. An internal user-wide revocation operation supports future password reset/deactivation workflows, but it is not exposed and has no authorization policy here. Future callers must be explicitly authorized to revoke other users' sessions. Retention and cleanup remain Pending Approval; no cleanup job is implemented.

Fake-repository tests simulate digest collisions, concurrent activity advancement, and revocation conflicts. They do not establish PostgreSQL atomicity, isolation, or real concurrent request guarantees. Future database tests must cover issuance versus credential reset/deactivation, validation versus revocation, conditional activity updates, concurrent logout, uncertain commit outcomes, and unique digest collisions. Revocation blocks future validations after commit; it cannot cancel operations already authorized and in flight. Sensitive writes will need in-transaction revalidation or an approved locking/serialization rule.

The session service remains disconnected from the production CredentialVerifier, FastAPI dependencies/routes, browser cookies, CSRF, MFA, authorization, administrator provisioning, and audit writing. The default production verifier remains unconfigured and fail-closed.

## Offline login and logout orchestration (Task 10F.4)

`backend/app/core/login_orchestration.py` composes the existing credential-verification and session-lifecycle services through injected boundaries only. It is not registered as a production authentication dependency and exposes no HTTP endpoints. `LoginInputPolicy` requires explicit bounds; the test values are development configuration, not an approved company password policy. Login input objects and successful result wrappers redact their representations and reject generic serialization. The result retains the existing one-time `IssuedSession` delivery object rather than copying its raw token; only a future trusted HTTP adapter may call its explicit cookie-delivery accessor after successful persistence.

The login sequence checks input bounds and an injected attempt-protection decision before password verification, then records the verification outcome/releases any acquired concurrency permit, evaluates a trusted server-side authentication-completion policy, and only then issues a session. Unknown, inactive and incorrect credentials remain generic rejections. Infrastructure or policy failures are sanitized and fail closed. No invalid, incomplete, denied, stale, or uncertain path returns a successful login result. A successful credential check is not MFA evidence: any future completion evidence must be issued by trusted server-side challenge handling and bound to the local user UUID and credential-version snapshot. No caller-supplied boolean can complete MFA. The test-only policy may explicitly permit completion solely for offline tests; there is no production password-only default.

The attempt-protection protocol separates a pre-verification `check` from a `finish_credential_check` result (or `None` when verification infrastructure failed). A future implementation must apply consistent policy to known and unknown usernames, account/source limits, global resource protection, concurrent KDF capacity, and success/failure accounting. Trusted request-source data must come from a validated deployment boundary. Distributed enforcement, retention/privacy controls for source information, thresholds, outage behavior, and monitoring require approval. The protocol itself provides no operational brute-force protection. No lockout threshold, persistent counter, retry delay, or limiter is implemented.

Logout asks the existing session service to revoke only the token presented for the current session; it does not update activity, delete records, or expose user-wide revocation. Results distinguish revocation, already revoked, absent, malformed, and uncertain outcomes. A future HTTP adapter should clear the local cookie for all outcomes, including uncertain persistence, while preserving the server-side result accurately. Clearing a cookie does not revoke a copied token; uncertain server revocation must not be reported as success. Repeated logout is safe and independent sessions remain unaffected.

The orchestration only carries forward the existing rehash recommendation. It does not generate or store a replacement hash, change credential version, or revoke sessions. A future parameter-only rehash must conditionally update the exact credential version/hash originally verified so it cannot overwrite a concurrent password reset. Password change, reset, and deactivation are separate workflows.

Future persistent login must make session insertion atomic with current active-account and credential-version checks. A pre-issuance read is insufficient against password-reset/deactivation races. MFA completion must be bound to the same identity/version and revalidated at issuance. If a commit outcome is uncertain, no token may be returned; a persisted orphan session may remain inaccessible because only its digest is stored, and a separately designed reconciliation/compensation strategy may be needed. Concurrent logout, validation, activity updates, and attempt-counter updates require conditional transactions and real PostgreSQL concurrency tests. Revocation prevents later validations after commit but cannot cancel work already authorized in flight. Offline fakes do not prove these guarantees.

Task 10F.4 adds only offline orchestration and fake-port tests, including one bounded Argon2id-to-session end-to-end test. It does not activate authentication, MFA, throttling, account provisioning, permission grants, sessions in a database, audit writing, cookies, CSRF, or routes. All AUTH-01–AUTH-15 decisions remain Pending Approval.

## Isolated authentication HTTP adapter (Task 10F.5)

`backend/app/api/v1/routes/authentication.py` defines a router factory for `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, and `GET /api/v1/auth/session`. Callers must explicitly inject the existing offline orchestration/session services, strict input/body limits, an origin allowlist, a CSRF validator, immutable cookie configuration, and a UTC clock. The operational `api_router` does not import or include this module; tests mount it only on a private in-process FastAPI test app. There are no persistence repositories, fake production dependencies, environment switch, account provisioning, password reset, or operational route registration.

Login requires one JSON object with exactly `username` and `password`, strict strings, configured character/UTF-8 limits, the expected JSON media type, and a bounded streamed body. Content-Length is an early check only; streamed bytes are counted independently. Origin and CSRF checks happen before body parsing or password work. Schema errors omit Pydantic values/details so submitted passwords are never echoed. A successful response contains only `authenticated` and local `user_id`; the raw session token is delivered solely by `Set-Cookie` after the orchestration confirms session persistence.

The adapter requires an explicit `__Host-` cookie name, Secure, HttpOnly, Path `/`, and no Domain. SameSite (`strict`, `lax`, or `none`) and a positive maximum cookie age are explicit configuration, not defaults; SameSite and final origin/deployment selection remain pending approval. Both Expires and Max-Age are bounded so browser retention cannot outlast the issued session expiry. Logout deletion uses the same host-only scope and security attributes. Browser expiry is not a substitute for server-side validation. No token enters JSON, URLs, localStorage, or sessionStorage.

Origin validation compares parsed scheme, IDNA host, and effective port against an exact configured allowlist. Wildcards, `null`, malformed/multiple origins, unexpected scheme/host/port, and missing Origin on state-changing requests are denied. Missing Origin may be explicitly allowed for safe GET status checks; if supplied, it must still match. No forwarded host is trusted, CORS remains a separate middleware concern, and existing operational CORS configuration was not modified.

**CSRF remains deliberately deferred.** The router requires a trusted injected `CsrfValidator` for both login and logout and fails closed when evidence is absent, rejected, malformed, or the validator is unavailable. HTTP tests use a fake-only double-submit comparator; it is not a production CSRF implementation and is not registered anywhere. Before activation, select and implement a complete mechanism (for example a synchronizer token or cryptographically signed, session-bound double-submit token), including an anonymous pre-login token flow for login CSRF. HttpOnly and SameSite alone are insufficient; the session token is never a CSRF token. Do not activate the router with a permissive validator.

Session status reads the cookie only, rejects invalid/expired/revoked/ineligible/stale sessions generically, returns only authenticated state and local user UUID, and does not return authorization or employee data. It calls the existing session validator with `update_activity=False`; status polling therefore does not extend idle lifetime. Other authenticated activity policy remains governed by the session service. Logout requires Origin and CSRF validation before processing; it revokes only the presented token and clears the local cookie for accepted logout requests. A 204 means the idempotent logout request completed (it does not reveal whether a row existed); uncertain server-side revocation returns sanitized 503 while still clearing the browser cookie. Rejected cross-origin/CSRF requests never clear it. Cookie clearing alone cannot invalidate a copied token.

If session persistence succeeds but response-time clock validation, cookie preparation, or response delivery fails, the adapter must return no session token. The persisted row may then be an inaccessible orphan because only the digest is stored. Any operational implementation needs a reviewed failure/reconciliation strategy and transaction evidence; this offline adapter does not claim to compensate or clean such rows.

Responses set `Cache-Control: no-store`, `Pragma: no-cache`, and a safe request ID. Mappings include malformed JSON 400, invalid fields 422, oversized body 413, wrong media type 415, origin/CSRF rejection 403, generic credentials/session failure 401, attempt-policy denial 429 (not evidence of an operational limiter), unavailable authentication/session/CSRF infrastructure 503, and unexpected failures 500. Login-completion denials share generic invalid-credential output. Logout uncertainty returns 503, not false success. Error bodies never include account status, internal reasons, exception strings, submitted values, or tokens.

Tests use an isolated in-process FastAPI app, fake orchestration/session/CSRF boundaries, fictional tokens and an HTTPS test base URL; no public test server is created. The API router test confirms the operational router lacks these endpoints. Existing request logging records method/path/status/request ID only; future proxies, APM, and access logs must redact request bodies, Cookie, Set-Cookie, CSRF headers, and authorization material. This is HTTP contract testing, not real browser SameSite/CORS behavior, production CSRF assurance, database persistence, or operational authentication.

Task 10F.5 does not modify the React frontend, operational CORS, the application route registry, database models/migrations, accounts, roles, audit writing, or production authentication. All AUTH-01–AUTH-15 decisions remain Pending Approval. Task 10F.6 should perform combined offline contract/security review, including end-to-end orchestration through this isolated adapter and explicit confirmation that only approved test-only policies are used.

## Initial account and identity model

Reuse the existing `users`, `roles`, and `user_roles` models. Keep the stable local `users.id` UUID as the application principal and audit actor. The initial operating plan is two named, individual accounts assigned the same proposed `inventory_admin` role. Do not constrain the database to exactly two users; two is an initial operational expectation, not a permanent schema rule. The approved schema change may add a password hash to the existing user identity rather than create a duplicate user table. Role assignments continue through `user_roles`; capability checks remain in backend policy and service dependencies.

Provisioning is restricted to an approved operator procedure. Account owners set their own credentials through a supervised setup flow or another explicitly approved secure channel. Do not use shared administrator credentials or default passwords. Public self-registration and public password recovery remain disabled. Account creation, password reset, deactivation, and role assignment must be attributable administrative actions.

Application users are not employee records. Employee synchronization does not provision, activate, deactivate, or assign roles to application users. An optional `users.employee_id` link remains separate and requires an approved mapping. Management AIOS users are also separate; no user, role, or administrator assignment is copied automatically.

## Credential data contract (schema implemented offline; operational policy proposed)

Prefer a separate `public.user_password_credentials` table for local password material. One row per eligible local `users.id` keeps secrets out of general user queries and gives future OIDC identities a separate extension point. Do not create another user table and do not impose a two-account database limit. Reuse `users.username` as the login name: it is already `VARCHAR(100) NOT NULL` with a unique case-insensitive `lower(username)` index. Do not duplicate username or add an independent normalized username column to the credential table. `users.email` is not the login key. Continue to use `users.status` for account activation; credential row existence means local password enrollment, so do not add a second credential active-state field.

Proposed username handling is to trim surrounding whitespace, normalize Unicode to NFC, then case-fold before storing/comparing against the existing `users.username`. Reject empty values and control characters; do not silently change a user's chosen name beyond the documented normalization. Confirm whether usernames may contain Unicode/confusable characters before implementation. Existing rows must be checked for canonical collisions before any normalization; if PostgreSQL collation and the application normalization do not enforce equivalent uniqueness, review a matching database constraint/index before activation. The normalization and character-set policy remain Pending Approval under the account-provisioning decision.

| `user_password_credentials` column | Proposed type and rule | Purpose |
|---|---|---|
| `user_id` | `UUID PRIMARY KEY`, FK to `public.users(id) ON DELETE RESTRICT` | One local password credential per stable application identity; retain audit references |
| `password_hash` | `TEXT NOT NULL` | Argon2id PHC encoded hash only; validate algorithm/encoding in application code |
| `password_changed_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` | Server-generated UTC instant of successful set/change/reset |
| `credential_version` | `INTEGER NOT NULL DEFAULT 1`, `CHECK (credential_version > 0)` | Increment on reset/change to invalidate sessions created against older credentials |
| `created_at`, `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` | Standard server timestamps; update timestamp on hash/version changes |

The table has no username, email, raw password, reversible credential, password hint, lockout counter, or free-text reset reason. Account deactivation remains `users.status`; provisioning keeps an account inactive until a credential is enrolled. No `must_change_password` column is proposed because no temporary-password flow is approved; add a constrained field only if the approved enrollment policy requires it. Protect hash reads from general runtime/reporting queries and never include hashes or credential fields in API schemas, audit metadata, logs, error responses, or exports.

Future company identity federation may use a separate optional `user_identities` mapping keyed by immutable `(issuer, subject)` and referencing the same `users.id`. Do not store IdP tokens in `user_password_credentials`, map by mutable email, or provision accounts through employee synchronization. A future summary service identity remains separate from human credentials.

## Password authentication contract (proposed)

- For password-only administrator authentication, the proposed minimum is **15 characters**. Count Unicode code points consistently, preserve the exact submitted password (do not trim or normalize it), support long passphrases, and do not truncate. Set a generous maximum input bound to protect parsing and hashing resources only after review. The minimum, maximum, and any composition rules remain Pending Approval under AUTH-03; do not impose unnecessary character-composition rules.
- Use a maintained Argon2id implementation and its safe verify/rehash APIs. Store the full encoded PHC string only; never store plaintext, reversible passwords, hints, or credential values in logs. Parameters (memory, iterations/time cost, parallelism, version) are configurable deployment settings, not user-controlled values. Benchmark on representative production hardware under expected concurrent login load and memory limits; select parameters that resist offline guessing while keeping login latency and concurrent memory use within an approved service budget. Rehash after successful verification when approved parameters are stale, in a transaction that also preserves version and session-revocation rules. No hashing library is selected or installed in this design task.
- Do not require periodic password changes absent evidence of compromise or an approved policy. A password change/reset updates the hash and timestamp, increments `credential_version`, and revokes all active sessions in one transaction.
- Return the same generic invalid-credentials result for an unknown username, wrong password, and inactive account. Never return account-existence details. Rate-limit by suitable account and network signals, add bounded backoff/temporary protection under an approved policy, and monitor abuse without logging submitted usernames/passwords or tokens in clear text.
- Apply the same throttle path to known and unknown usernames, with a dummy password-hash verification for unknown names where needed to reduce timing-based enumeration. Avoid permanent account lockout that could be used for denial of service. In-memory limits alone are inadequate across multiple instances/serverless workers. AUTH-03 and deployment controls remain pending.
- Password changes require the current authenticated session or approved attributable recovery. Administrative recovery is not a public endpoint and one administrator is not automatically authorized to reset the other's credentials. See the controlled provisioning/recovery procedure below.
- Credential verification and session-store failures fail closed with a generic service-unavailable response; they never grant preview or administrator access.

**MFA recommendation:** require MFA before administrator access is exposed over the internet. Prefer a phishing-resistant company-approved method where available; a company-approved authenticator-based method is a fallback. ## Browser session contract (schema implemented offline; runtime policy proposed)

Prefer a backend-managed opaque session after password verification. Generate a cryptographically secure random token, store only its cryptographic hash, and send it only in a host-only `HttpOnly`, `Secure` cookie with an approved `SameSite` setting. Do not store passwords or session tokens in browser localStorage, URLs, or JavaScript-readable storage. Rotate session identifiers after login and relevant credential/privilege changes; logout revokes the current session.

The proposed session record includes local user ID, unique token hash, created/last-seen timestamps, expiry, revocation timestamp/reason, and only minimal approved client metadata. Enforce server-side expiry and reject revoked sessions. Password reset and account deactivation revoke that user’s active sessions in the same transaction as the account change where practical. On every request, confirm that the local user remains active and load current roles/permissions. Concurrent session limits and whether password changes revoke all devices require approval.

The proposed initial limits are an **8-hour absolute lifetime** and **30-minute idle timeout**; both are Pending Approval under AUTH-06. Each session also has an absolute `expires_at` that cannot be extended by activity. Validate expiry, revocation, current user status, idle time, and credential version on each authenticated request. Session validity is not authorization: reload current roles and capabilities per request. A removed/expired role reduces access at the next authorization check without needing to destroy the session.

| `auth_sessions` column | Proposed type and rule | Purpose |
|---|---|---|
| `id` | `UUID PRIMARY KEY DEFAULT gen_random_uuid()` | Internal session row identity; never used as the browser secret |
| `user_id` | `UUID NOT NULL FK public.users(id) ON DELETE RESTRICT` | Stable local principal; preserve audit history |
| `token_hash` | `BYTEA NOT NULL UNIQUE`, check `octet_length(token_hash) = 32` | SHA-256 digest of a cryptographically random 256-bit opaque token |
| `credential_version` | `INTEGER NOT NULL`, check `> 0` | Snapshot from `user_password_credentials` used to invalidate prior sessions |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` | Server-generated creation instant |
| `last_seen_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` | Server-generated last-activity instant |
| `expires_at` | `TIMESTAMPTZ NOT NULL`, check `expires_at > created_at` | Absolute expiry, set at creation and never extended |
| `revoked_at` | `TIMESTAMPTZ NULL` | Server-generated invalidation instant; null means not explicitly revoked |

Use a unique index/constraint on `token_hash`, an index supporting active sessions by `(user_id, revoked_at)`, and an expiry index suitable for bounded cleanup. Do not store the raw token, IP address, user agent, device fingerprint, or free-text revocation reason. Add a constrained reason code only if an approved incident/recovery workflow requires it; otherwise record an authorized security event without credential material. All timestamps represent UTC instants (`TIMESTAMPTZ`); application serialization uses UTC. No session retention or cleanup period is approved. Cleanup may delete only expired/revoked rows after the retention and audit requirements are approved.

Generate the raw session secret with a cryptographically secure random generator only after credential verification/MFA and account eligibility checks. Return the raw value once in a cookie; persist only its SHA-256 digest. Its high entropy makes a fast cryptographic digest appropriate for lookup (password hashes remain Argon2id). Rotate rather than reuse any pre-authentication identifier. Insert the session and establish its credential-version snapshot in a transaction; if password reset races login, serialize on the credential row or condition session insertion on an unchanged version so a session based on an old password cannot become valid after reset commits.

On every request, look up the digest and require: `revoked_at IS NULL`, `expires_at > database_now`, `last_seen_at` within the approved idle window, active `users.status`, and session credential version equal to the current credential version. Logout sets `revoked_at` once and is idempotent. Password reset/change increments the credential version and revokes all active sessions transactionally. Deactivation changes `users.status` and revokes sessions in the same transaction. Future requests fail after commit. A request already authorized before logout/reset/deactivation may still be in flight; for sensitive writes, revalidate within the business transaction and define a lock/serialization protocol with revocation so an in-flight request cannot commit after a revocation that should take precedence. This ordering policy requires approval and PostgreSQL concurrency tests.

Avoid a write on every request by updating `last_seen_at` with a conditional database statement no more often than once per **5 minutes** per session, as an initial design proposal. The 5-minute throttle is Pending Approval; it bounds writes but means persisted activity may lag actual activity by up to that interval. Validate idle expiry against the persisted timestamp before accepting a request; do not refresh an already-idle session. Use server time and an atomic conditional update so concurrent requests cannot move activity backward. Concurrent session count/eviction policy remains pending; do not silently terminate another administrator's session.

For unsafe methods, use an approved CSRF defense (synchronizer token or equivalent), validate `Origin` (and `Referer` as defense in depth), and use narrowly configured CORS. CORS alone is not CSRF protection. Require HTTPS and secure deployment headers. Authenticated sensitive responses use `Cache-Control: no-store` (and appropriate private-cache policy); never cache session or credential responses in shared caches.

The current frontend and API deploy separately, so cross-origin cookie behavior must not be assumed. Prefer an approved same-origin API proxy/reverse proxy or co-hosted frontend/API origin. A same-site subdomain arrangement is a second choice and must be validated with real browsers; credentialed CORS must allow only exact approved frontend origins. Cross-site cookie authentication is not recommended because browser third-party-cookie restrictions can break it. Any proxy must use a strict backend destination allowlist and contain no browser-visible proxy secret. Do not change deployment configuration in this design task.

Proposed cookie: host-only `__Host-inventory_session`, `Secure`, `HttpOnly`, `Path=/`, and an approved `SameSite` value (recommend `Lax` with CSRF token and Origin validation; `Strict` may be used if navigation requirements pass). Do not set `Domain`. The `__Host-` prefix requires `Path=/`; if a narrower cookie path is chosen, reassess the prefix and protection tradeoff. Never store passwords, raw session tokens, or long-lived auth credentials in `localStorage`, URLs, or JavaScript-readable persistent storage. Session renewal is server-side and must not turn the absolute expiry into an indefinitely sliding lifetime.

## Session and credential lifecycle

1. **Provisioning/enrollment:** create or select an approved inactive local user; an authorized operator assigns the unique canonical username. The account owner enters their own password through the approved hidden-prompt/setup procedure. Store the Argon2id hash and incremented credential version; activate only after setup and approved role assignment succeed. No default password or self-registration.
2. **Login:** normalize the submitted username using the approved canonicalization; apply the same rate-limit behavior to unknown names and perform dummy hash work where selected. Verify password and MFA (if required), recheck user is active, then create a new session. Set the secure cookie only after transaction success.
3. **Validation:** validate digest, revocation, absolute/idle expiry, active user, credential version, and then current role assignments/permissions. Authentication does not cache authorization.
4. **Logout:** revoke the current session server-side, expire the cookie, and return a safe result. A future shared identity-provider logout is not assumed; local logout invalidates this Inventory session only.
5. **Password change/reset:** require current authenticated proof or authorized recovery. Replace the hash, update timestamp/version, and revoke all sessions atomically. Force new MFA or enrollment only if approved.
6. **Deactivation:** set existing `users.status` inactive, revoke sessions in the same transaction, deny requests even if stale session rows remain, and preserve the local user UUID for audit history.
7. **Role changes:** keep the session but reload current valid role assignments on each request; access reduces immediately on subsequent checks. No administrator bypass or implied approval permission.
8. **Expiry cleanup:** scheduled cleanup is future work; first approve retention, backup, and audit obligations. Cleanup must be bounded and must not remove user, employee-history, or audit identities.

The proposed 8-hour absolute / 30-minute idle values and five-minute activity-write throttle are not company-approved settings. Concurrent sessions are Pending Approval; alternatives include allowing multiple sessions with per-session logout, a small approved cap, or one active session with explicit user notice. Forced eviction is not recommended without a recovery path.
